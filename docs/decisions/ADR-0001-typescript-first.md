# ADR-0001：首版使用 TypeScript 与 Node.js

- **状态：** Accepted
- **日期：** 2026-07-29

## 背景

KFC 的首要目标是亲手理解编程 Agent 的控制循环、Provider 边界、工具协议、上下文、权限与验证机制。P0 需要快速建立可执行 CLI、确定性测试、配置和错误边界，同时让每个设计选择可以被观察和重构。

技术选择必须服务这个学习目标，而不是追求语言声望、理论性能或过早的最终形态。

## 候选方案

### TypeScript + Node.js

优势：

- CLI、JSON、HTTP、流式事件和异步迭代可以使用同一语言表达。
- 类型系统足以约束消息、事件、工具参数和错误联合类型。
- 编译与测试反馈快，适合逐步暴露边界后重构。
- Node 标准库已经覆盖参数解析、文件系统、进程、HTTP 和取消信号等首版需求。

代价：

- 类型在运行时被擦除，外部输入仍需 Zod 等运行时校验。
- 交付依赖 JavaScript 运行时或预构建产物。
- 对低层进程隔离、资源限制和单文件分发的控制不如系统语言直接。

### Rust

优势是运行时开销可控、类型与所有权约束更强，并适合未来的低层沙箱、进程管理和单二进制分发。

当前代价是所有权、异步 Trait、错误类型和跨平台系统细节会与 Agent Loop 的学习目标竞争注意力。在核心边界尚未通过真实任务稳定前，这些成本缺少足够收益。

### Python

优势是实验快、AI/数据生态成熟，适合原型和研究脚本。

当前代价是核心消息、事件、工具 Schema 和大型重构更多依赖运行时纪律。KFC 希望在仍能快速迭代的同时获得更强的编译期结构反馈，因此不作为首版 Core。

## 决定

P0–P6 使用 Node.js 22+ 与严格 TypeScript 实现单进程 CLI Core。外部数据通过运行时 Schema 校验；核心模块使用显式类型、领域错误和依赖注入保持可测试性。

当前不建立 Rust Core，也不进行多语言拆分。辅助工具可以在不污染 Core 边界的前提下使用适合自身任务的语言或直接可运行模块。

## 已获得的实际证据

P0 开发中，TypeScript 严格检查已经发现：

- 安装 `@types/node` 后仍需显式启用 Node 类型。
- `noEmitOnError` 对阻止错误构建产物非常重要。
- `exactOptionalPropertyTypes` 区分了字段缺失与显式 `undefined`。
- CLI 命令、配置来源、领域错误和 Doctor 依赖可以使用普通类型与注入进行确定性测试。

与此同时，当前实现没有出现需要 Rust 才能解决的性能、内存、沙箱或分发问题。

## 影响

得到：

- 更短的实验反馈周期。
- 统一的 CLI、Provider、事件和测试语言。
- 足够严格但允许快速重构的类型边界。

失去：

- 原生单二进制和更直接的系统资源控制。
- Rust 编译器提供的所有权与线程安全保证。
- Python AI 生态中部分现成实验工具的便利。

## 重新评估条件

只有出现真实证据时才重新考虑 Rust Core 或多语言拆分：

- Shell、沙箱或权限隔离需要 Node 无法可靠提供的系统级控制。
- 已测量的启动、内存或吞吐瓶颈影响用户任务。
- 单文件、无运行时分发成为明确发布要求。
- Agent Core 边界已经由大量真实任务稳定，迁移范围可被清楚定义。
- 安全审查证明某个高风险执行模块需要更强的语言级约束。

不会因为“Rust 更高级”“重写可能更快”或竞品使用某种语言而迁移。
