# KFlow Code Vision

**状态：** P0 范围定义  
**日期：** 2026-07-29

## 为什么做 KFC

成熟的编程 Agent 已经能够完成大量开发任务，但仅仅会使用它们，无法回答其行为为何可靠、为何失败，以及怎样修改其边界。KFlow Code（KFC）的目的不是复制某个产品的外观，而是通过亲手实现关键机制，将编程 Agent 从黑盒还原为一个可解释、可验证、可演进的工程系统。

项目长期希望理解并实现 MCP、Skills、会话、沙箱、Hooks、权限机制、Git 分支以及 `/xxxx` 命令等能力。最终目标是形成对 Agent 开发的独立理解，能够自行开发 Agent、完成真实开发任务，并更灵活地利用 Agent 参与工程工作。

KFC 可以暂时不如成熟产品，但必须能够持续吸收优秀实现、解释设计差异，并通过实验不断迭代。

## KFC Mini v0.1.0 的核心闭环

首版只验证以下最小闭环：

> 接收任务 → 调用模型 → 读取代码 → 修改代码 → 执行测试 → 根据证据判断是否完成

这个闭环必须具备明确的状态、错误边界、终止条件、权限约束和验证证据。任何不能帮助验证该闭环的功能都不进入首版。

## 首版明确不做

- MCP、Skills 和 Hooks
- Subagents、多模型及多 Provider
- TUI、IDE 插件和复杂交互界面
- 云端同步与跨设备会话
- 自动 Git 分支及 Worktree 管理
- 完整的斜杠命令系统

这些能力不是永远不做，而是在核心闭环稳定、真实需求出现后再逐项引入。抽象必须由已经发生的问题换取，不能由想象预支。

## 怎样才算学会

掌握一个机制，必须同时做到：

1. **能解释**：不用术语遮掩，说清它解决的真实问题。
2. **能还原**：不照搬成熟项目，独立完成最小实现。
3. **能验证**：覆盖正常、异常和边界路径。
4. **能取舍**：说明选择、代价和重新评估条件。
5. **能调试**：依据状态、事件、日志和证据定位失败。
6. **能迁移**：在其他项目中重新实现或组合该机制。
7. **能比较**：读懂优秀实现，并解释设计差异背后的约束。

每个阶段至少沉淀四类证据：可运行实现、自动化测试与真实任务记录、学习笔记、架构决策或阶段复盘。

## 项目原则

- 先提出第一性问题，再选择技术和抽象。
- 一次只引入一个主要架构概念。
- 代码完成不等于任务完成；完成必须有可复现证据。
- 先写自己的假设，再借助 AI 审查和补充反例。
- 先做单 Agent 的可靠闭环，再增加扩展能力。
- 失败、错误假设和重构原因都属于学习成果，必须记录。
